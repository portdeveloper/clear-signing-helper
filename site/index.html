Clear Signing Helper

From a deployed contract to a registry pull request that passes the registry's own checks. It derives everything the ABI, compiler output, deployment records and verified source can prove, asks a human only for what they cannot, and never guesses. Every claim on this page links to the code behind it.

0.3.0-preview.1npmMIT GitHub · npm · the registry

The problem

A hardware wallet shows raw hex for a transaction unless the protocol has published an ERC-7730 descriptor in the Ethereum Foundation's registry. Getting one accepted means writing JSON by hand, writing a test file whose expected text must match a wallet renderer to the character, and learning whether it was right after opening the pull request.

Where each stage lives: inputs foundry.ts, abi-project.ts, fetch.ts · scaffold descriptors.ts with evidence from evidence.ts, ast.ts, broadcast.ts · decisions and apply in app.ts · validator descriptors.ts and priors priors.ts · fixtures and rendering fixtures.ts over the vendored renderer · export, lint and runners app.ts, lint.ts, runners.ts · add-deployment registry-edit.ts.

Operating principle (CLAUDE.md). Derive everything provable deterministically. Let a person or an AI propose only what cannot be derived, and record who decided. Verify everything verifiable against the registry's own tools. Never re-encode calldata, never bind an address on its name alone, never submit on the owner's behalf.

What it does

Drafts from evidence

Functions, argument paths and types from the ABI (scaffold). Intents and labels from NatSpec, enums from the compiler AST, token constants from constructor arguments recorded in broadcasts (evidence.ts, ast.ts). Deployment bindings from broadcasts (broadcast.ts) or from the verified source at an address with proxies resolved (fetch.ts). Every value carries its source (provenance).

A file for the judgment calls

decisions writes one file per contract with the slots only a human can fill: intent wording, which token an amount is in, what to hide and why, what to exclude and why (writeDecisions). Each slot shows hints: NatSpec, what other registry descriptors do with the same selector (priors.ts), candidate denominations. apply validates and writes everything back (applyDecisions).

Exact test expectations

Example transactions are rendered through the same Sourcify renderer wallets use (fixtures.ts, renderer provenance, hash check). The rendered text becomes the registry test file (registry.ts) and a snapshot your CI checks on every change (runTests). Recorded broadcast transactions can be fixtures directly (broadcast.ts).

The registry's checks, locally

Export lays the bundle out as the registry expects (exportBundle), runs the registry's formatter and linter (lint.ts), then both implementations its CI tests against, at the versions it pins (runners.ts). If anything fails, there is no bundle.

Add a chain in one command

For a protocol already in the registry, registry add-deployment fetches the verified ABI at the new address, proves every described function exists there, appends the deployment, renders a test case for the new chain (registry-edit.ts), and leaves a two-line diff by inserting into the existing text (json-edit.ts).

Refuses to guess

An unverified address (SOURCE_UNVERIFIED), a different contract at an address (ABI_MISMATCH), a token whose symbol is unknown on the new chain (NO_RENDERABLE_TEMPLATE), a hidden native value (UNDISPLAYED_NATIVE_VALUE): each is refused with the reason and nothing is written. The decisions stay with the owner.

Get started

# Node 22+. Foundry only for Foundry projects. uv enables the registry's linter.
npm install --global --ignore-scripts clear-signing-helper@preview

# From a verified address
clear-signing init --address 0xYourContract --chain-id 143 --owner "Your Protocol"
clear-signing decisions --contract clear-signing/abi/YourContract.json:YourContract
#   fill intents, denominations, show/hide, exclude; set "author"
clear-signing apply --decisions clear-signing/decisions/YourContract.json
clear-signing fixture --name stake --contract <id> --function 'stake(uint256)' --args '["1000000000000000000"]' --chain-id 143 --to 0xYourContract
clear-signing preview --fixture clear-signing/fixtures/stake.json
clear-signing review --accept && clear-signing test --update
clear-signing export --strict-portability --registry-runners --out bundle

# Protocol already in the registry, new chain
clear-signing registry add-deployment --registry ./registry-clone \
  --descriptor registry/weth/calldata-weth.json --chain-id 143 --address 0x... --token 0x...=WMON:18

Inside a Foundry repository, forge build once, then clear-signing init; the tool also reads NatSpec, enums and broadcast records there. Full command reference in the README; the agent playbook is the skill.

Each of these solves a different slice. Reach for Cyfrin's tool to read what a transaction does or to compute Safe and ERC-8213 hashes; for Ledger's builder when you want a device-shaped preview in a browser; for erc7730 to author EIP-712 descriptors. This tool's job is the last mile the others stop before: the test file, the registry's own checks before the PR, and the one-command chain addition.

Status

  • Published: 0.3.0-preview.1 on npm and as a GitHub prerelease, byte-for-byte identical (release record, verification script).
  • First real submission: registry PR #3003, a staking contract on Monad testnet, produced entirely by the tool. All 13 registry checks passed on the first push; maintainer review pending (dogfood record, including what still needed a human).
  • Measured against the registry: the validator accepts 261 of 284 merged descriptors; the rest use nested-call or encrypted fields, which are out of scope by design (acceptance script, recorded run).
  • Tested: 47 automated tests (test/, CI), the registry's full corpus of 283 descriptors and 605 real transactions (registry-compatibility.test.ts), a mined Anvil deposit (anvil.test.ts), and a mocked Sourcify for offline CI (abi-mode.test.ts).
  • Not yet: EIP-712 descriptors, adding a chain to an EIP-712 descriptor, and a cold run by a team that did not build it (roadmap).
